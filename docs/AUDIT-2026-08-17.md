## 3. Findings — documentation against code

### F-01 — The roadmap defers a feature that has shipped

```text
Severity:    High (for a documentation finding)
Status:      FIXED in this pass
Area:        Docs · roadmap
Confidence:  High
```

**Evidence.** `docs/ROADMAP.md:332` listed `E2EE DMs (NIP-44)` under
"Explicitly deferred". `client/src/nostr/nip44.rs` is 519 lines of shipped
implementation, checked against the specification's own test vectors
(`client/src/nostr/nip44.vectors.json`, committed as a fixture), and
`cargo test --workspace` runs them.

**Why it matters more than a stale line.** The roadmap is the document the
project points contributors at for "what is not built yet." A reader deciding
what to work on would have found the highest-value privacy feature in the
project listed as available. The last audit's A-03 was the same shape — the
roadmap describing a system that did not exist — in the opposite direction.

## 5. What is verified, and what is still only reasoned

The suite is green and the gates are clean, which is worth less than it sounds
unless the boundary is stated:

**Verified by executed tests.** The wire protocol end to end (the integration
suites drive a real gateway through the bot SDK), permissions and owner
controls (22 tests), voice token minting including a scripted per-request
failure, guild export/import, persistence across a restart, the rendezvous
handshake, NIP-44 against the specification's published vectors, and the
routing table's non-member exclusion.

**Not verified anywhere, and the list has not moved:**

- **No Nostr DM path has ever run against a real relay.** The commit that
  shipped it says so in its last line. The tests cover the crypto and the
  event construction; nothing covers a live `wss://` relay accepting, storing
  and returning a gift-wrapped event.
- **Nothing has run between two machines.** The QUIC tests run both ends in one
  process over loopback, which settles the plumbing and nothing about NATs,
  advertised addresses, or whether a remote joiner lands on the private path.
- **No port mapping has been observed on a real router** in CI.
- The 9 ignored tests (live SFU, Windows loopback capture, macOS screen
  capture) need hardware no runner has. The Windows one found a heap corruption
  in shipped code the first time a human ran it, which is the argument for
  running them by hand periodically rather than treating them as decoration.

## 8. Deferred-work register


The successor to `TODO.md`, recovered in full from `git show 686808a^:TODO.md`
(851 lines, 68 entries) and re-checked against the tree at `54d6175`. Section
names are kept verbatim, because ~33 source comments cite them ("see … under
Voice / audio") and those citations now resolve here.

Scope is unchanged from the original: *things we know we want but chose not to
ship in the commit that surfaced them.* Reasoning that took a measurement to
establish is not repeated here — where an entry says a thing was measured, the
measurement is in the git history of the file it names.

**Status key.** **Open** — verified still open today, check named. **Unblocked**
— open, and a dependency that was holding it has since landed. **Partly
closed** — some of what the entry asked for has shipped. **Unverified here** —
a product, ops or hardware question this host cannot settle.

### How to read this

**The numbers are identifiers, not positions.** Commits, pull requests and the
register's own cross-references cite them, so an entry keeps its number when it
closes, moves group, or is folded into another. Gaps in the sequence are
expected and are not missing entries.

Grouped by what an entry *is*, because the count is the point: a register where
an accepted trade-off, a roadmap aspiration and a real defect all read as "open"
cannot answer "how much is left". **Live work** is the only group that should be
counted as pending.

### Live work

#### Project

1. **No `LICENSE` file.** Defaults to all rights reserved, contradicting the
   contributing sections. A decision for both copyright holders, not a code
   change; interacts with whether licence exceptions are ever sold (that needs a
   CLA before the first outside PR). — **Open** (`ls LICENSE*` → absent)

#### Discordia design adoption

2. **Deferred decorative elements from the comps.** Day-streak, "Send a tip",
   "Relay op", org-"Verified" badges have no backend. — **Open**

3. **The palette icon is not where the comp puts it.** The comp puts it in the
   top bar; `AppearanceButton` renders from `UserPanel` at the sidebar bottom.
   — **Open**

#### Security

5. **A username may contain control characters, and nothing strips them.**
   `canonical_username` trims and truncates; it does not filter control
   characters, and the same is true of guild/channel names. — **Open**

6. **The gateway is plaintext, and `wss://` looks supported without being.**
   — **Partly closed.** The `wss://` half is fixed: `Cargo.toml:24` now builds
   `tokio-tungstenite` with `rustls-tls-webpki-roots` (added for Nostr relays),
   so a `wss://` URL connects instead of failing after `net.rs` normalises into
   it. The gateway also gained an encrypted, key-authenticated front door in
   `server/src/quic.rs`. What remains: the plain TCP listener still serves
   cleartext, so this is a deployment question rather than an impossibility.

#### Repo & CI

7. **macOS clippy gates one profile of two.** — **Open**

8. **The Windows portable and setup ship the wrong icon.** Reported from a real
   download. — **Unverified here**

9. **Windows SmartScreen blocks the download as an unknown publisher.** —
   **Unverified here** (needs a signing certificate decision)

10. **The macOS build is not notarised**, so a recipient has to defeat
    Gatekeeper. — **Unverified here**

11. **`Discordia.html` should be named and moved, not deleted** — it is the
    design source. — **Open** (still at the repo root)
71. **Nothing checks that a test would fail if the code it guards broke.**
    A green suite says the tests ran, not that they are testing anything. On
    2026-08-17, breaking guarded behaviour on purpose found **three** tests in
    this repo's own new work that passed while proving nothing: one compared two
    error messages that could never match, one asserted a property the gateway
    already enforced somewhere else, and one accepted *any* error where only one
    error meant the guard had held. All three were written the same day by
    somebody who believed they were careful.
    The instrument is mutation testing — `cargo-mutants` — and the scoping is
    the whole question. Measured on this host: 1,082 functions in `src/`, a
    warm suite of 18s, and a per-mutant cost dominated by the incremental
    rebuild rather than the run. A whole-workspace pass is estimated at **35–45
    hours** serially (the client is 636 of those functions and links
    libwebrtc); `--in-diff` over one branch is **25–60 minutes**.
    **So it belongs in CI, not on a laptop.** A job that mutates only the diff
    on each pull request costs a runner rather than a developer's afternoon, and
    it asks the question at the moment the answer is cheapest to act on.
    `cargo mutants --list` reports the mutant count in seconds and would turn
    the estimate above into a measurement before anyone commits to a schedule.
    — **Open**

18. **Operator UX polish.** No visual distinction between a system-guild operator

22. **Nobody has performed the channel-reorder *drag*.** The menu path has eight

#### Platform — bots (Tier 1) & activities (Tier 3)

25. **Privileged intents have a confirm step, not a verification flow.** The
    confirm step shipped; there is still no review, no scale threshold, and
    nothing stopping an owner granting intents to any key. — **Partly closed**

27. **Activity remote URLs.** Needs a CSP story, an allowlist mechanism and
    per-origin capability grants before arbitrary remote activities load. — **Open**

28. **Per-call activity consent.** `message.send` is granted wholesale at launch.
    — **Open**

29. **Activity channel binding.** — **Closed.** An activity now carries the
    channel it was launched from, and both `message.send` and `channel.get`
    answer from that rather than from whatever is selected when the call fires.
    An activity opened in #general used to post to #off-topic if the user had
    wandered there, and nobody was told. The bundled dice activity re-read its
    target after every send *because* the answer could go stale under it; one
    read is enough now, and its comment says so.

#### Decentralization / rendezvous

30. **The macOS local-network grant is declared but never exercised.**
    `NSLocalNetworkUsageDescription` was added prophylactically; the path that
    would prove it (LAN self-host from a *bundled* app, friend joining) has not
    been run. — **Open**

32. **A relay older than `can_publish` still grants publish, and nothing detects
    it.** The field defaults to `true` on the relay so older *hosts* keep
    working; the mirror is that an older *relay* silently signs publish. Closing
    it properly means versioning the rendezvous protocol. — **Open**

34. **Signed "guild moved" redirect.** After an export/import migration old
    members still point at the source instance (roadmap P6 tail). — **Open**

#### Client UX

36. **The Windows client is a console application, so every release ships a `cmd`
    window beside it.** — **Closed.** `#![cfg_attr(not(debug_assertions),
    windows_subsystem = "windows")]`: release is windowed, debug keeps the
    console, because that is where `dx serve` and a terminal run are read.
    Both halves landed together, as the entry required. `livekit-server` is
    spawned with `CREATE_NO_WINDOW` and piped stdio, its output forwarded line
    by line into our own log — so the SFU's account of a failed self-host
    survives instead of merely moving off-screen. The `tasklist`/`taskkill`
    calls beside it and `open_external`'s `cmd /C start` carry the same flag;
    without it a link click would flash a console.
    What replaced the console as the diagnostic channel:
    `%APPDATA%\dioxusfun\logs\discordia.log` (under `config_dir`, so
    `DIOXUSFUN_CONFIG_DIR` moves it), rolled at 5 MB with one generation kept,
    plus a panic hook — a release panic previously wrote to a stderr that did
    not exist, which made the one event most worth a record the one that left
    none.
    **The 139 console writes were answered without touching them.** `SetStdHandle`
    points the process's own stdout/stderr at that same file, so every
    `eprintln!` in the crate lands in it. That is why this closed as a change to
    `main.rs` rather than a diff across seventeen files with a level chosen for
    each line — and the count can now drift as far as it likes without the
    problem coming back. Converting them to `tracing` is still worth doing for
    the levels and the filter; it is no longer load-bearing.

77. **The macOS `.app` keeps only half of what entry 36 gave Windows.** The log
    file and the panic hook are not platform-gated, so a release build writes
    both wherever it runs. The `SetStdHandle` redirect *is* Windows-only, and a
    bundle launched from Finder has no stderr either — so on macOS the ~139
    `eprintln!` diagnostics are still lost, and there the fix is `dup2` onto the
    log fd or converting the call sites. Not urgent: the same code paths log
    their failures through `tracing` as well in most cases. — **Open**
    (`open -a Discordia`, then `~/Library/Application Support/dioxusfun/logs/`

37. **The fade-in never re-triggers on the connect and identity-setup panels.**
    `rsx!` represents a key only on the **root** node of a body, so a nested key
    is dropped — measured against dioxus 0.7.10 with a four-case probe. The dead
    attributes are gone; restoring the re-trigger means putting the key on a body
    root, and it is not yet established that a changed key remounts a single
    non-list child rather than diffing in place. — **Open**

38. **Live-session username rename.** — **Closed.** `UpdateUsername` mutates
    the three places a name lives — the global directory, the member row in
    every guild, and the `User` the connection carries — and broadcasts a
    `MemberUpdate` to exactly the guilds that changed. The connection's own copy
    matters as much as the rows: it is what the *next message* is attributed to,
    and a member-row update alone would rename you in the sidebar while your
    posts kept the old name.
    Unsigned on purpose, unlike the name in `Identify`: by the time this arrives
    the connection is authenticated as the key it claims, and a display name is
    not a claim about anybody else. Canonicalised with the same
    `canonical_username` the handshake uses, so nothing arrives in a shape
    Identify would have refused.
    **A bot cannot send it at all** — the gateway holds bots to an allowlist of
    three message types. `rename_user` also skips bot rows so an installed bot
    keeps its installer's label (entry 26), but that guard never runs today; it
    is defence in depth for the day the allowlist grows, and the test asserts
    the door that is actually shut rather than the one behind it.

    "show the server directory while you have not joined a server, communities
    once you have". This client is always inside a session past the connect

    reads *community membership on this host* instead, and the three cases it
    can distinguish are in its tests. Settling it properly means a client that
    can sit in home with no gateway at all, which is a real change: `net.rs`,
    `WorkspaceView` and every panel assume a connection. Worth doing, because it
    is also what would let someone use the DM half of the app before they have
    anywhere to connect to. — **Open** (launch against a bare host: home leads
    with Servers; join one community, it leads with Communities)

    `ServersPane` submits `SessionMode::ByCode`, which covers the directory and

    forms `connect.rs` already renders; the reason they are not here is that
    `SelfHost` starts a server in this process while another session is live,
    and nothing tears the old one down first. — **Open**

#### Nostr / direct messages

70. **A DM is sent to the relays *we* chose, not the ones the recipient reads.**
    `nip17::dm_relay_list` publishes our own kind:10050 and the service
    subscribes to it, but `nip17::parse_dm_relay_list` — the reader — has no
    caller, so nobody else's list is ever consulted. This works while both ends
    default to the same relays and silently does not when they do not: the wrap
    is published successfully, to somewhere the recipient never looks. Closing
    it needs a per-recipient subscription for kind:10050 and publish routing per
    conversation, which is more than wiring the existing reader. — **Open, and
    deliberately not taken on** (2026-08-17). Three things a scoping pass
    established, so the next attempt starts from them rather than rediscovering
    them:

    - **It cannot bite inside Discordia today, and that is fragile rather than
      safe.** `dm_relays` defaults to empty and falls back to `DEFAULT_RELAYS`,
      and **nothing in the UI sets it** — `git grep dm_relays` finds only the
      fallback in `workspace.rs`. Every user is therefore on the same four
      relays. The gap opens at the interop boundary the feature was sold on: a
      correspondent on another Nostr client with different relays receives
      nothing, and the sender's message shows as sent.
    - **The work is the pool, not the reader.** `parse_dm_relay_list` is
      written and tested. `RelayPool::connect` builds its `senders` once and
      the fan-out task captures them, so the pool can neither gain a relay at
      runtime nor publish to a subset — both of which this needs. That is a
      rewrite of the pool's core, larger than the five entries closed on
      2026-08-17 put together.
    - **It contains a privacy decision, which is why it is not an
      implementation task.** Honouring a peer's kind:10050 means *the other
      party chooses which servers this client dials*, so a correspondent can
      learn our IP by publishing a relay list pointing at their own server —
      and the list needs a cap before it becomes a connection amplifier. The
      project's stated threat model is third parties rather than the host, and
      this moves that line. Settle it before writing code.

    A smaller step exists that closes the silent half without opening the
    dialling half: subscribe to the peer's kind:10050 and *say* when it does not
    overlap ours, turning "the message vanished" into "this contact reads
    elsewhere". No dynamic pool, no new connections.
    (`#[allow(dead_code)]` on `parse_dm_relay_list` names this entry)

### Compatibility with clients we cannot identify

39. **Nothing on this wire can tell an old client from a new one, and five
    things depend on that.** *(Folded together on 2026-08-17 from what were
    entries 39, 40, 41, 50 and 67 — five symptoms with one cause, which made
    the register read as five decisions when it is one.)*

    - `ClientMessage::SetScreenShare` still carries a `channel_id` nothing
      reads. Kept because serde drops fields a struct does not name, so an old
      client talking to a new server still works and the reverse would not.
    - `ScreenShareState` is still sent, derived from `screen_sharing`, purely
      so a client older than that flag keeps its LIVE badge.
    - An old client can render a webcam in the screen tile: camera and screen
      share one room and the bare identity, told apart only by `TrackSource`.
      Inherent to reusing the room — the property that made the camera cost no
      new token.
    - A peer on an older build cannot watch a natively captured share: the
      macOS publisher uses `{pubkey}#video` and older clients resolve sharers
      by bare pubkey, so they sit on "Connecting to stream…" with no error.
    - An old client that mutes reads as deafened, because it sent
      `deafened: muted` before the deafen button existed.

    **The half that is closed:** `Identify` carries `client_version` and the
    server logs it, so an operator can count what is connected, and a client
    old enough to have these bugs is identifiable by *absence* — it sends no
    version at all. **The half that is not:** the field is self-declared and
    unauthenticated (the signature covers `nonce || pubkey || username` and not
    it), so it can inform a decision and cannot gate a peer.

    So this is one question, not five: **when do we stop supporting clients
    older than X?** Answering it closes all five at once; nothing else does,
    and no amount of per-symptom work will. — **Open**

### Found by the mutation run (§10)

Entries the 2026-08-17 mutation run turned up: places where the behaviour can be
broken and no test objects. None is a bug today — the code is correct — and each
is numbered from 72 so it does not collide with entries added on other branches.

72. **The raid detector has no test at all.** `AppState::
    note_join_and_maybe_panic` is the mass-join detection that auto-locks a
    guild past 10 joins per minute — the project's only automatic anti-abuse
    control. It survives being replaced with a function that does nothing, and
    survives deleting the `!` in `!already`, which would make it fire only when
    panic mode is already on. Seven mutants in total, none caught. Testing it
    needs no new machinery: the threshold is 10 joins in 60 seconds and the
    integration harness can drive eleven joins.
    Worth pairing with a second gap the same code shows: the threshold and the
    proof-of-work difficulty are **hardcoded constants**, so a large guild
    legitimately exceeding 10 joins/minute locks itself out and a small one
    cannot ask for a lower bar. — **Open**

73. **The rendezvous challenge nonce is not asserted to be fresh.**
    `verify::fresh_nonce` survives being replaced with a constant. A fixed nonce
    makes every ownership signature replayable by anyone who has seen one — the
    exact property the challenge/response exists to provide, and the thing
    standing between a claimed name and whoever watched somebody claim it. The
    generator is correct (`OsRng`, 32 bytes); nothing checks that it stays that
    way. A test that two connections receive different nonces is three lines.
    — **Open**

74. **Retention can stop deleting without anything noticing.**
    `AppState::sweep_retention` survives returning 0, and the cutoff arithmetic
    (`days * 86_400_000`) survives `*` → `+` and `*` → `/`. A guild that has set
    a retention policy is making a promise about data not being kept; nothing
    tests that the promise is carried out, only that the setting can be stored.
    — **Open**

75. **The Nostr DM service loop and `net.rs` are largely unguarded.**
    `client/src/nostr/service.rs`: 20 of 22 mutants survive — the task that owns
    the relay pool and feeds `AppState`. `client/src/net.rs`: 107 survive — the
    `apply()` match that mutates client state from every server message.
    The contrast is the useful part: the layers *below* the service (`nip17`,
    `event`, `nip44`, `nip02`, `nip59`) are the best-defended code in the
    repository, at 125 caught against 13 survivors, because the specification's
    own test vectors are committed as a fixture. The wiring above them has
    almost nothing. — **Open**

76. **Input validation has no tests.** `sanitize_channel_name` (3 survivors),
    `AppState::sanitize_role` (3), `is_hex_color` (2). Cheap to close and the
    kind of function whose rules drift silently. — **Open**

### Closed

Left in place with the verdict, because what an entry claimed before it was
closed is often the most useful part — three of these turned out to be wrong

13. **Blob GC.** — **Closed**, by mark-and-sweep rather than the refcounting
    this entry called for: the live set is derivable from the database at any
    moment (`Store::referenced_media`), so nothing has to be maintained and a
    wrong answer needs a bug in one query rather than in every writer.
    `MediaStore::sweep` runs hourly after the retention sweep — retention is
    what creates orphans — and will not touch a blob younger than 24 hours, a
    `.tmp` file, or anything at all if the reference query failed.

19. **Invite expiry / use limits.** — **Closed server-side; the UI is the
    remaining half.** `Invite` now carries `expires_at_ms`, `max_uses`, `uses`
    and `created_by`; `CreateInvite` accepts a TTL and a cap, and `GuildInvite`

    completed, and refunded if the joiner turns out to be banned. A spent code
    is refused with the *same* message as an unknown one, so it cannot be used
    as an oracle for "this guild exists". **Still open:** the invite panel is

20. **A reorder can be silently half-applied, and the client cannot tell.**
    — **Closed, and the entry was wrong about the scope.** It blamed the
    `UpdateChannel` arm for being silent "unlike the arms around it"; in fact
    **14 of the 17** rate-limited arms were silent and three were not. Every one
    of them now calls `reject_rate_limited`, so the client is told in all
    seventeen cases. What remains is not a defect: a big first reorder can still
    exhaust the budget, because the limiter is doing its job.
    *(Original text follows.)* The
    `UpdateChannel` arm dropped rate-limited excess with `continue` and no
    `Error`, so the list was left visibly half-reordered. Fuel was reduced (a one-slot move costs two messages) but a
    guild that has never been reordered still renumbers every row.
    — **Unblocked.** The entry defers the real fix because
    `server/src/gateway/connection.rs` was being rewritten on the
    `networking-direct-and-private` branch. **That branch merged as #76**; the
    file is stable and the fix — an error on rejection, which makes *every*
    silent rate-limit drop visible — is now reachable.

21. **A reorder writes back a stale snapshot of every row it renumbers.**
    — **Closed**, by the position-only message this entry asked for:
    `ReorderChannels { guild_id, positions }`. `UpdateChannel` is a full
    replace, so a concurrent edit to `name`/`topic`/`read_only`/
    `slowmode_secs` on a renumbered row used to be overwritten by a client that
    did not intend to touch it. The new frame carries positions and nothing
    else, checks `ManageChannels` once for the guild, and refuses ids that
    belong to another guild.
    It also finishes the half of entry 20 that the limiter left behind: one
    frame for the whole move instead of one per row, so a guild whose channels
    have never been reordered — every position 0, so all of them renumber —
    no longer spends its entire rate-limit window on a single drag.

26. **Bot identity refresh.** — **Closed: the installer's label wins**, and
    deciding that turned up more than a cosmetic inconsistency. The roster
    already showed the installer's name, but a message's author was built from
    the connection's self-declared user — so a bot installed as "PingBot" could
    post as "Server Admin", in the surface where a name is most likely to be
    believed. `push_message` now resolves an installed bot's display name from
    its `BotInstall`, per guild, since the same bot can be installed in two
    guilds under two names. A human's declared name is untouched: the Identify
    signature commits to it, and it makes no claim about anybody else.

31. **Reservation display fields are persisted but never read.** — **Closed by
    removing them.** The entry left the choice open — "fine if this is
    groundwork for an offline browse listing; dead weight otherwise" — and
    `discover()`'s own contract settles it: offline reserved names are excluded
    *on purpose*, because you cannot join a host that is away. So there is no
    listing for the display fields to feed, and a host that comes back
    re-supplies `name`, `description` and `public` in its `Register` frame
    before anything is shown. `Reservation` is now `slug` + `owner_pubkey`.
    Older `reservations.json` files still load — which is load-bearing rather
    than incidental, because `Registry::load` treats an unparseable file as
    *start empty* and only logs a warning, so an incompatible change would have
    silently un-claimed every name on the relay. There is a test for exactly
    that, and it fails under `deny_unknown_fields`.

33. **Name release / rename.** — **Release closed; rename deliberately not
    built.** `HostToRendezvous::ReleaseName` gives a name back, proved by the
    same Schnorr signature over `SHA256(nonce || pubkey || name)` that claiming
    it used — one verifier, two operations. It is refused while a session is
    live under that name, because releasing then would leave the running host
    on a code anyone could immediately claim; the owner is asked to stop the
    host first. A stranger's attempt is refused with the *same* message a name
    nobody has claimed gets, so it cannot be used to enumerate which offline
    names are taken — the question `/discover` also declines to answer.
    **Rename is not built and release does not quite substitute for it.**
    Release-then-claim works but is not atomic: if the new name turns out to be
    taken, the old one is already gone. An atomic `RenameName` needs a
    signature binding *both* names — the current construction signs one — so it
    is a protocol design question rather than a missing branch.

## 10. Mutation run, 2026-08-17

The suite is green, which says the tests ran. This section is about whether they
would notice if the code broke. Every behaviour below was broken **on purpose**;
a mutant that "survives" is a change to the program that no test objected to.

**Method.** `cargo-mutants 27.1.0`, `-j4`, on the host in the header. 5h09m of
wall clock over 1,828 mutants — a subset of the 3,224 the tool generates for the
whole workspace, chosen as described under *Scope* below. The tool was removed
afterwards; it is not a dependency of this project and nothing in the tree
references it.

Two configuration decisions are worth recording because each one cost a failed
run to find:

- **`TMP` must be short.** cargo-mutants builds in a temp copy of the tree, and
  the default path is long enough that `cl.exe` hits `MAX_PATH` compiling
  `webrtc-sys` — the first attempt returned *6 of 6 unviable* with a missing
  abseil header. `TMP=C:/mut` fixes it. This is the same MAX_PATH class that
  bites builds under deep worktree paths.
- **`--test-package`, never `--test-workspace`.** A mutant in `protocol` is
  caught by the *server's* tests, so testing only its own package reports
  survivors that are really just untested-from-there — a false finding is worse
  than a slow run. But testing the whole workspace rebuilds the client (and
  webrtc) per mutant, measured at 2–6 minutes each. Naming the consumers gets
  the honesty without the C++.

### Scope, and what was deliberately left out

| Package | Mutants run | Caught | **Survived** |
|---|---|---|---|
| `dioxusfun-protocol` | 41 | 32 | **0** |
| `dioxusfun-bot` | 26 | 12 | **0** |
| `dioxusfun-rendezvous` | 111 | 44 | **3** |
| `dioxusfun-server` | 706 | 336 | **234** |
| `dioxusfun` (selected files) | 686 | 241 | **368** |
| `dioxus-grid-layout` | 258 | 100 | **127** |

Counts exclude *unviable* mutants (did not compile) and *timeouts* (hung the
test), neither of which says anything about test quality.

**Left out on purpose:** the client's `features/**` (1,400+ mutants of UI, where
a survivor says little) and the platform capture modules `sysaudio`, `sysvideo`
and `rawmic` — their tests are `#[ignore]`d for want of hardware, so every
mutant there would survive and report something already known.

### What survived, and which of it matters

**A survivor is not a bug.** The code is correct today; a survivor marks a place
where breaking it later would go unnoticed. Most of the 732 are noise, and
saying which is the point of this section.

#### Findings worth acting on

1. **The raid detector is entirely untested.** `AppState::
   note_join_and_maybe_panic` — the mass-join detection that auto-locks a guild
   past 10 joins/minute — can be **replaced with a function that does nothing**
   and the suite stays green. Seven mutants survive it, including deleting the
   `!` in `!already`, which would make it fire only when panic mode is already
   on, i.e. never. This is an anti-abuse control with no test at all.

2. **The rendezvous challenge nonce can be a constant.** `verify::fresh_nonce`
   survives being replaced with a fixed string. Nothing asserts the nonce is
   fresh — and a fixed nonce makes every ownership signature replayable
   forever by anyone who observed one, which is the property the whole
   challenge/response exists to provide.

3. **Retention can silently stop deleting.** `AppState::sweep_retention`
   survives returning 0, and the arithmetic that computes the cutoff
   (`days * 86_400_000`) survives `*` → `+` and `*` → `/`. A guild's retention
   promise could quietly become a no-op.

4. **The Nostr DM service loop is unguarded.** `client/src/nostr/service.rs`:
   20 of 22 mutants survive. The layers beneath it are the best-tested code in
   the repo (below); the task that drives them is not.

5. **`net.rs` — 107 survivors.** The `apply()` match that mutates client state
   from every server message. Large surface, no unit coverage of most arms.

6. **Input validation with no tests:** `sanitize_channel_name` (3),
   `AppState::sanitize_role` (3), `is_hex_color` (2).

7. **Two of ours, from the same day.** `Invite::is_live` (2) and
   `RateLimiter::allow`'s eviction boundary (`>` → `>=`) survive. Both are
   exact-boundary conditions — the value at precisely the window edge — and are
   recorded rather than fixed, because the behaviour there is arguably a matter
   of taste rather than correctness.

#### The same weakness, found a third way

`AppState::slowmode_check` has a test, and two mutants still survive it. One
changes `secs - elapsed` to `secs + elapsed` — the *"wait N seconds"* number the
user is told. The test asserts that posting is refused; it never looks at what
the refusal says.

That is the third instance in one day of the same shape: **a test that asserts
something was rejected without asserting which rejection it was.** The other two
were the proof-of-work gate (which could not fail at all) and a rendezvous
release test that accepted any error. It is worth treating as a review question
rather than a coincidence.

#### What the run vindicated

The DM cryptography is the best-defended code in the repository, and by a wide
margin:

| Module | Caught | Survived |
|---|---|---|
| `nostr/nip17` (chat semantics) | 14 | **0** |
| `nostr/event` (ids, signatures) | 17 | **0** |
| `nostr/nip02` | 17 | 1 |
| `nostr/nip59` (gift wrap) | 13 | 4 |
| `nostr/nip44` (encryption) | 64 | 8 |

That is what committing the specification's own test vectors as a fixture buys,
and it is a concrete argument for doing the same wherever a spec offers them.
`protocol` and `bot-sdk` also came back at **zero** survivors.

#### Noise, named so nobody re-triages it

Roughly 500 of the 732 are not worth a test: `identity::color_signature` (12 —
it derives an avatar colour from a pubkey), `Debug`/`PartialEq` impls,
`server/src/main.rs`'s CLI paths (23), `e2ee.rs`'s JS-bridge string builders (50
— they talk to a webview that no test runs), and `grid-layout`'s geometry
helpers (127 — a self-contained UI widget). The alarming-sounding "45 survivors
in `identity.rs`" is almost entirely the colour function; the key handling
itself is caught.

### What this changes about the numbers

A count of passing tests answers "how many ran", and this repository has been
quoting that number. The count that would answer "how much is defended" is the
kill rate, and it is now known for 1,828 mutants: **765 caught of 1,497 viable,
or 51%.** Interpreting that fairly needs the noise removed — the UI and
platform-bridge survivors are not debt anyone should pay — but even so, the two
findings above (a raid detector with no test, a nonce that need not be fresh)
are the kind that a green suite is supposed to prevent and did not.

Entry 71 in §8 proposes the standing form of this: `cargo-mutants --in-diff` in
CI, mutating only what a pull request changes, where it costs a runner rather
than five hours of somebody's machine.
