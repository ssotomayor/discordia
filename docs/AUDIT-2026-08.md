that produced it, and what is actually true versus what the documentation
claims. Every finding below carries the command or file that established it.

## 2. Architecture as built

The `CLAUDE.md` diagram matches the code. Verified component by component; the
only drift found was in `README.md` (see **A-04**).

**Server** (`server/src/`, 11.4k lines, **zero `unsafe`**) — axum gateway,
one task per socket in `gateway/connection.rs`, authoritative `DashMap` state in
`state/mod.rs`, write-through SQLite in `store.rs`. The write-through claim holds:
`persist()` (`state/mod.rs:18`) logs and continues, exactly as documented.

**Fan-out** is a per-connection routing table, as claimed. `deliver(targets, msg)`
resolves pubkeys through `conn_ids_by_pubkey`; bounded per-connection `mpsc`
(`CONN_QUEUE_CAP = 256`, `state/mod.rs:27`) drops slow consumers to force a
reconnect-and-resnapshot.

**Client** (`client/src/`, 23.8k lines) — Dioxus 0.7.10 desktop. All 107 `unsafe`
occurrences live in five platform modules (`rawmic/windows.rs` 31,
`sysaudio/windows.rs` 30, `sysaudio/macos.rs` 20, `sysvideo/macos.rs` 17, plus 8
across `webview2.rs`/`main.rs`/`devlog.rs`/mod files). **`protocol`, `server`,
`rendezvous`, `bot-sdk` and `grid-layout` contain no `unsafe` at all.** That
containment is a real architectural strength and is worth protecting.

**The three-identity screen room** described in `CLAUDE.md` is accurate:
bare `{pubkey}` (webview: renders everything, captures screen on Windows,
publishes camera everywhere), `{pubkey}#audio` (native, subscribe-only — and its
token really is minted without publish rights, `livekit.rs:175-203`), and
`{pubkey}#video` (native macOS screen publisher).

`MintRequest` (`server/src/livekit.rs:10`) is **not** a wire type despite its
name — it is the argument to the in-process `VoiceTokenMinter` trait. The actual
rendezvous wire enum is `HostToRendezvous` in `protocol/src/rendezvous.rs`, which
has exactly one variant (`Register`). The `protocol`-is-the-only-wire-source rule
therefore holds; the naming just invites the opposite conclusion.

### A-01 — Server-supplied strings are interpolated into webview JS unescaped

```text
Severity:    High
Status:      FIXED in the follow-up pass
Area:        Security / client · webview bridge
Confidence:  High (injection primitive), Medium (impact ceiling — not executed)
```

**Evidence**

- `client/src/features/screenshare.rs:1083-1085` —
  `document::eval(&format!("{SCREEN_JS}\nwindow.dxScreen.connect('{url}','{tok}');"))`
- `protocol/src/lib.rs:1148-1151` — `ScreenToken { livekit_url: String, token: String, … }`
- `client/src/net.rs:861` — `s.screen_token = Some((livekit_url.clone(), token));` — stored verbatim
- `grep -rn "livekit_url" client/src` — **no validation or escaping on any path**
- Counter-example in the same files: `screenshare.rs:1065` and `camera.rs:44` both use
  `serde_json::to_string(&device)` precisely to embed a possibly-quoted device name safely

**Finding.** `livekit_url` and `token` arrive from the gateway as free-form
`String`s and are pasted into single-quoted JavaScript string literals with no
escaping. A URL containing `'` closes the literal and everything after it
executes as JavaScript in the client's webview. The same shape appears at the
other `document::eval(&format!(…))` call sites; those interpolate hex pubkeys,
UUIDs and preset-table constants, which are safe *by construction of their
source* rather than by any check at the sink.

**Why it matters.** The threat model makes this reachable, not theoretical.
Joining someone else's server is the product's headline use case ("connect by
code" to a stranger's rendezvous), so a hostile gateway is an expected actor —
and the gateway is plaintext (`TODO.md`, Security), so a network attacker on the
path can inject the same string without operating a server at all. Injected
script runs with the webview's access to the rendezvous bridge (`dioxus.send`),
the rendered DOM (messages, usernames, guild contents) and outbound network. The
Nostr private key is held in Rust and on disk, not in the webview, so it is not
directly readable — which bounds the impact but does not remove it.

**Verification.** Read the format string, the wire type, and every assignment
path for `livekit_url`; confirmed absence of any sanitiser. Not executed against
a malicious server — hence Medium confidence on the impact ceiling specifically.

**Recommendation.** Apply the pattern the same files already use: build the
arguments with `serde_json::to_string(&…)` and interpolate them without
surrounding quotes. That is a mechanical change at a handful of sites and
introduces no new dependency. Validating `livekit_url` parses as a `ws(s)://`
URL on receipt in `net.rs` would be defence in depth.

### A-02 — A display name over 32 characters permanently prevents connecting

```text
Severity:    High
Status:      FIXED in the follow-up pass (regression-tested)
Area:        Auth / client UX
Confidence:  High (reproduced)
```

**Evidence**

- `server/src/gateway/connection.rs:93-94` — sanitises **then** verifies:
  `let username = sanitize_username(&username); … auth::verify_identify(&pubkey, &signature, &nonce, &username)`
- `server/src/gateway/connection.rs:1734-1740` — `sanitize_username` = `trim()` + `chars().take(32)`
- `client/src/net.rs:176-180` — the client signs the **raw** `params.username`
- `client/src/features/identity_setup.rs:180-184` — display-name input has **no `maxlength`**
  (12 other inputs in the client do have one)
- `client/src/identity.rs:239-242` — `set_display_name` stores without validation

**Finding.** The server canonicalises the username before checking the
signature, but the client signs the pre-canonical form. Any name the sanitiser
alters therefore produces a signature over different bytes than the server
verifies, and the handshake fails.

**Reproduced** with a temporary integration test against a real gateway
(`Bot::connect_as_user`, which signs identically to the client), reading the
first frame the server returns:

```text
 5-char  'alice'    -> READY (stored username = "alice")
32-char             -> READY
33-char             -> ERROR: identify rejected: signature did not verify
padded '  bob  '    -> ERROR: identify rejected: signature did not verify
empty ''            -> ERROR: identify rejected: signature did not verify
```

Of the three failing cases, only the length one is reachable from the real
client: `identity_setup.rs` trims at all three entry points and disables the
button on an empty name, but nothing anywhere caps length.

**Why it matters.** A user who types a 33-character display name is locked out
of every Discordia server, permanently — the identity is written to disk before
the first connect, so relaunching does not help. The diagnostic actively
misleads: it says the *signature* failed, which points at key corruption or a
protocol mismatch, not at the name. This is a plausible first-run experience,
not an edge case.

**Verification.** Probe test written, executed, and deleted; tree confirmed
clean afterwards.

**Recommendation.** Make the client canonicalise before signing, so it signs
what the server will store — a shared helper is the durable fix, since the
sanitiser lives server-side and the two must not drift again. Failing that,
`maxlength: 32` on the input plus the same cap in `set_display_name` closes the
reachable path. Server-side, rejecting a non-canonical username with a message
that names the problem would have turned this from a lockout into a prompt.

### A-03 — ROADMAP describes two architectural seams that do not exist

```text
Severity:    Medium
Status:      FIXED in the follow-up pass
Area:        Documentation / architecture
Confidence:  High
```

**Evidence**

- `docs/ROADMAP.md:73-75` — "Two seams make this possible … **`Store`** — durable
  state (async trait; SQLite or Postgres via `DATABASE_URL`). **`Bus`** — event
  delivery (`LocalBus` in-process; `NatsBus` only in cluster mode)."
- `server/src/store.rs:48` — `pub struct Store` — a **concrete struct**, not a trait
- `grep -rn "trait Bus\|LocalBus\|NatsBus\|struct Bus"` — **zero matches in the workspace**
- `grep -rn "DIOXUSFUN_MODE\|DATABASE_URL\|BUS_URL\|discordia.toml"` — **zero matches**,
  though `docs/ROADMAP.md:128-129` lists all four as Phase-2 deliverables and marks
  Phase 2 "✅ mostly shipped (env config …)"

**Finding.** Three separate overstatements. (1) `Store` is a struct; adding
Postgres requires *introducing* an abstraction, not writing a second impl.
(2) No `Bus` trait exists in any form. What shipped under "Phase 5a transport
Bus ✅" is a per-connection routing table inside `AppState` — a good design, and
the status header describes it accurately, but the phase body still lists the
trait as the deliverable and the run-mode table still has a "Bus" column
promising `in-process` / `NATS + Redis`. (3) The run-mode table's "one binary,
chosen by config" has no config to choose with: there is no mode selector.

**Why it matters.** ROADMAP is the document a contributor or evaluator reads to
judge how far cluster mode is. It currently implies the hard part (the seams)
is done and only the implementations are missing. The reverse is true. `TODO.md`
is accurate on this point ("The Store API and TEXT/INTEGER encodings were
designed for it, but only the SQLite impl exists"); `CLAUDE.md` is nearly so.
ROADMAP is the outlier.

**Recommendation.** Reword the two seam bullets to describe what exists (a
concrete `Store` whose API and encodings were designed to be portable; a routing
table in `AppState`) and move the trait extractions into Phase 7's scope, where
the work actually is. Drop or mark-as-unbuilt the four config names.

### A-05 — The TLS entry in TODO.md misstates the dependency situation

```text
Severity:    Medium
Status:      Entry CORRECTED; the underlying TLS gap stays open
Area:        Security / documentation
Confidence:  High
```

**Evidence**

- `TODO.md` (Security) claims: "`tokio-tungstenite` is pinned at 0.24 … with **no
  TLS backend in `Cargo.lock`** — no `native-tls`, no `rustls` among its
  dependencies"
- `grep -n 'name = "rustls"\|name = "native-tls"…' Cargo.lock` → **rustls (6726),
  native-tls (4755), openssl (5399), tokio-rustls (7797) are all present**
- `cargo tree -p dioxusfun -i rustls` → rustls **is compiled into the client**, via
  `reqwest` (a direct client dependency) and `livekit-api`
- `Cargo.toml:27` — the workspace already standardises on
  `reqwest = { …, features = ["json", "rustls-tls"] }`
- `Cargo.lock:8262-8277` — `tungstenite 0.24`'s dependency list genuinely contains
  no TLS crate

**Finding.** The *conclusion* is right — `wss://` cannot be dialled, because
`tokio-tungstenite` 0.24 is built without a TLS feature — and the trap it
describes is real: `net.rs:44-50` normalises `https://` → `wss://` and accepts
`wss://` as valid input that can never connect. But the stated *reason* is wrong.
TLS backends are not absent from the lockfile; rustls is already compiled into
the client binary today.

**Why it matters.** The entry uses "no TLS backend in `Cargo.lock`" to argue the
fix is heavy. The correction cuts the other way: enabling a TLS feature on
`tokio-tungstenite` adds no new dependency and no new supply-chain surface,
because the workspace already ships rustls for HTTP. The genuinely hard part
survives untouched — a self-hosted server at a home IP has no CA-issued
certificate, so key-pinning against the host's Nostr key (with its
accept-everything failure mode) is still the real design problem. Only the cost
estimate changes, not the difficulty.

**Recommendation.** Correct the two sentences at the source and keep the entry
open. Independently: `normalize_url` accepting a scheme that cannot work is a
one-line improvement — reject `wss://` with a message that says TLS is not
compiled in, rather than letting it fail later as a connect timeout.

### A-09 — No `[profile.release]` in the workspace

```text
Severity:    Informative
Status:      Open (by omission, not decision)
Area:        Build / packaging
Confidence:  High
```

**Evidence.** `grep -rn "\[profile.release\]" --include=*.toml` → zero matches.
The root `Cargo.toml` defines ten `[profile.dev.package.*]` overrides for the
tract/DeepFilterNet stack (with an excellent comment explaining why), but nothing
for release.

**Finding.** Shipped binaries use cargo defaults: `opt-level = 3`, no LTO,
`codegen-units = 16`, `panic = "unwind"`, no symbol stripping (the CI strips the
Linux server binary explicitly, at `ci.yml:256`).

**Why it matters — and a trap worth naming.** This is a missed size/speed
opportunity, not a defect. But it interacts with a documented behaviour:
`TODO.md` records that the bundled SFU is orphaned by any kill that skips
unwinding, because `LivekitSubprocess` relies on tokio's `kill_on_drop`. Setting
`panic = "abort"` — the usual first move when someone opens this file to shrink
the binary — would extend that orphaning to every panic path. Anyone adding a
release profile should read that entry first.

**Recommendation.** No action required. If a profile is added, `lto = "thin"` and
`codegen-units = 1` are the safe wins; `panic = "abort"` is not, for the reason
above.

### 4.1 What the follow-up pass deliberately did not fix

Naming these matters as much as the fixes: a reader who sees seven of ten
findings closed will otherwise assume the rest were missed.

- **The TLS gap itself (A-05).** Only the wrong *reason* was corrected in
  `TODO.md`. Turning the feature on is easy; deciding what a self-hosted server
  at a home IP authenticates *with* is not, and getting it wrong gives you a
  custom verifier whose failure mode is accepting everything. That is a design
  decision, and `TODO.md` says it is being worked out on a branch.
- **Windows clippy (A-07).** The test step landed because it has no prerequisite.
  Clippy still needs one throwaway CI run to enumerate what it finds, then a
  commit fixing those, then the gate — and the findings cannot be enumerated
  from this machine. Unchanged from what `TODO.md` already said.
- **Everything under A-08.** Those are tracked decisions with written reasoning
  (`Capability::ChannelRead` is "wire it up or drop it", which is a product call;
  the unread reservation fields may be groundwork). Closing them silently
  because they are small is exactly the "cleaning up something without checking
  why it was introduced" the audit warns against.
- **A-09 and A-10.** Recorded as informative, no action, and that has not
  changed. Adding a release profile in particular is a trap worth leaving alone
  until someone wants it — see the `panic = "abort"` note.
- **The `persistence` flake.** Still unreproduced, still open. Five clean runs
  are not a diagnosis.

## 5. What is well built and should not be "cleaned up"

Auditing for defects makes it easy to lose sight of what is already right. These
are load-bearing and were verified during this pass:

- **`server/src/auth.rs`.** The signed message is `nonce || pubkey_hex ||
  username`, which looks like a length-ambiguity hazard and is not: the nonce is
  server-chosen and fixed, and `XOnlyPublicKey::from_slice` forces `pubkey_hex`
  to exactly 64 characters, so the split is unambiguous. Uses
  `Secp256k1::verification_only()`. Nonce is 32 bytes from `OsRng`. Do not
  "improve" the concatenation without re-deriving why it is safe.
- **`sanitize()` in `server/src/media.rs:83-95`.** Whitelists `<64 hex>.<1-5
  alnum>` and nothing else, which closes path traversal at the only two read
  sites. The comment explains the reasoning correctly.
- **The Identify block** (`connection.rs:86-113`). Rejects a second `Identify`;
  calls `identify_conn` *before* snapshotting so no concurrent frame is lost; and
  treats bot-ness as self-declared with a written rationale for why inferring it
  from installs would be an attack. All three are non-obvious and all three are
  right.
- **Lock discipline around `.await`.** Spot-checked `ban_member`
  (`state/mod.rs:1418-1436`): the DB write is awaited *before* the `DashMap`
  entry guard is taken. No held-guard-across-await was found in the sampled
  mutations.
- **`unsafe` containment.** Five files, one crate, all platform FFI.
- **Zero bare `TODO`/`FIXME`/`HACK`/`XXX` markers in the entire workspace.** All
  12 marker hits are deliberate pointers *to* `TODO.md`. The convention
  established in `9429e3c` is being followed rather than merely written down.
- **`.cargo/config.toml`.** The `-ObjC` link flag for Apple targets carries a
  comment explaining the exact selector-lookup failure it prevents. This is the
  kind of comment that saves a day.

## 7. Limitations of this audit

Stated plainly, because an audit that hides its blind spots is worse than none.

- **Single platform.** Everything was compiled and run on Windows 11. The
  `cfg(target_os = "macos")` code — `sysaudio/macos.rs`, `sysvideo/macos.rs`,
  ~37 `unsafe` occurrences — was **read, not compiled or executed** here. Linux
  likewise.
- **No runtime exercise of media paths.** Voice, screen share, camera and
  system-audio capture were not run. The 6 `#[ignore]`d tests were not executed:
  no SFU, no display grant, no capture device in this environment. Every claim
  about audio/video *behaviour* in this document is sourced from the code or from
  measurements the repository itself records — none was independently reproduced.
- **No release build, no bundle, no installer, no Docker build.** `A-09` is from
  reading configuration; the Windows console-window and icon entries in `TODO.md`
  remain unverified here for the same reason, and `TODO.md` already says so.
- **Commit history: subjects and metadata for all 218; diffs for a selected
  subset** — the pivots, reverts-in-spirit, and commits touching areas under
  examination. This is not a line-by-line review of every diff.
- **A-01's impact ceiling is reasoned, not demonstrated.** The injection
  primitive is confirmed by reading the format string and the wire type; no
  exploit was written or run against a malicious gateway.
- **Not covered:** the `activities` sandbox in depth, `grid-layout` internals,
  the Tailwind build pipeline, and per-dependency licence review beyond what
  `TODO.md` already records.

## 8. Executive summary

**1. What state is the project actually in?** Healthy and unusually
self-aware. It compiles clean, 139 tests pass deterministically, there is no
`unsafe` outside five platform FFI modules, and there are zero orphan `TODO`
markers because deferred work is tracked in one place by an enforced convention.
The dominant risk is not rot — it is that documentation of *intent*
(`docs/ROADMAP.md`) has drifted ahead of what was built.

**2. Current architecture.** As described in `CLAUDE.md`, verified: axum gateway
with authoritative in-memory `DashMap` state and write-through SQLite; a
per-connection routing table for fan-out; a Dioxus desktop client that also hosts
an embedded server; up to three LiveKit identities in one screen room, with the
camera deliberately reusing the bare one.

**3. Critical problems.** None. Nothing found can corrupt data, lose messages, or
crash the server.

**4. High priority.** Two, both new: **A-01** (unescaped server-supplied
strings reaching `document::eval`, reachable via a hostile or MITM'd gateway) and
**A-02** (a >32-character display name locks a user out of every server,
with an error that blames the signature).

**5. Technical debt.** Well catalogued already. The real additions from this pass
are **A-07** (Windows CI runs neither clippy nor tests over the highest-risk
`unsafe` in the repo) and the documentation corrections.

**6. Incorrect documentation.** `docs/ROADMAP.md` promises a `Bus` trait, an
async `Store` trait and four config knobs that do not exist (**A-03**);
`README.md` omits the camera entirely (**A-04**); `TODO.md`'s TLS entry
states a wrong reason for a right conclusion (**A-05**); one comment still
references a wallet removed in July (**A-06**).

**7. Historical decisions still shaping the code.** The Solana→Nostr pivot
(cleanly executed, zero residue beyond one comment); the choice to reuse the bare
LiveKit identity for the camera (cheap, at the cost of a mixed-version rendering
hazard the server cannot mitigate); and the native macOS capture path, kept on
its merits after its original justification was found to be wrong.

**8. Do not touch.** `auth.rs`'s message construction, `media.rs`'s `sanitize()`,
the Identify ordering in `connection.rs`, the `unsafe` containment boundary, and
the `[profile.dev.package.*]` tract overrides — each is load-bearing and
non-obvious. See §5.

**9. Current risks.** A hostile gateway is in the threat model by design, and the
control channel is plaintext with no TLS path that works — that combination is
what elevates **A-01**. Secondarily, the Windows `unsafe` surface has the
weakest automated coverage of any platform.

**10. Do first.** **A-02** — smallest fix, worst user impact, fully
reproduced. Then **A-01**, using the escaping pattern already present in the
same files. Then **A-07**'s one-line test step.

**11. Justified as-is, do not "fix".** The three-identity screen room; the camera
reusing the bare identity; the transmit gate judging the denoised hop; stream
audio subscribed on publication rather than on watch; the deliberate 12-byte
allocation leak per Windows activation; the `#[ignore]`d hardware tests. Each has
a written rationale that survives scrutiny.

**12. Could not be verified.** Everything macOS and Linux; all runtime media
behaviour; release builds, bundles, installers and Docker; and the impact ceiling
of **A-01**. See §7.
